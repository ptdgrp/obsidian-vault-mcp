# Blueprint v3 External Body and Evidence Design

**Date:** 2026-07-19

## Summary

Blueprint v3 separates external, LLM-produced bodies from Blueprint protocol Markdown. External
bodies are stored inside tilde-fenced blocks and cannot contribute headings, links, block IDs, or
other syntax to the surrounding Blueprint document. Protocol-owned structure remains ordinary
Markdown generated by the service.

The same version introduces first-class Evidence submission and listing, structured Results-to-
Evidence references, a derived Todo Evidence index in the central Blueprint document, and short
sequential IDs for every entity except the Blueprint itself.

This protocol has not entered production. Version 3 is an intentional clean break: v2 documents,
v2 request shapes, and the `evidence_add` tool are not supported or migrated.

## Motivation

The v2 representation exposed implementation details to callers and allowed external Markdown to
interfere with protocol structure:

- callers could accidentally persist literal `\n` sequences instead of line breaks;
- an H2 in Evidence content could terminate the Evidence section and corrupt later sections;
- Todo Evidence was stored only in Todo files, leaving `blueprint.md` without an aggregate audit
  view;
- complete-close validation required a precise Markdown Evidence link but did not show the valid
  form;
- callers sometimes reopened a Definition of Done item merely to take the incomplete-close path;
- ULIDs made local Todo, DoD, Evidence, and Revision references unnecessarily long.

The existing requirements that completed Todos carry Evidence and that Blueprint execution uses an
explicit lifecycle remain intentional. Blueprint is a heavyweight orchestration protocol, not a
lightweight personal todo list.

## Content Model

### Protocol text

Protocol text is a short, single-line value that participates directly in Blueprint structure.
Examples include:

- Blueprint and Todo titles;
- owner, creator, completer, closer, and canceller names;
- close, cancel, block, and Revision reasons;
- Definition of Done and Completion Criteria item text.

Protocol text must be non-empty where required and must reject line breaks. The service escapes or
rejects characters that would change the containing Markdown construct.

### External body

External body content originates outside the Blueprint protocol and has an independent body
concept. It includes:

- Blueprint Intent, Constraints, Plan, Rubric, Results, and Notes;
- Todo Intent, Plan, Handoff, Results, and Notes;
- Evidence bodies.

Public requests represent an external body as lines rather than a raw multiline string:

```json
{
  "lines": [
    "1. Inspect the current state",
    "2. Run verification",
    "",
    "## This is external content, not a Blueprint section"
  ]
}
```

The service joins the lines with LF characters. An empty final array element represents a trailing
LF in the body. Required bodies must contain at least one non-whitespace character. This makes line
boundaries explicit in MCP input and prevents a caller from using a doubly escaped `\n` as a line
separator.

Every external body is stored in exactly one tilde-fenced block:

```markdown
## Plan

~~~
1. Inspect the current state
2. Run verification

## This is external content, not a Blueprint section
~~~
```

The default delimiter is `~~~`. If the body contains a line that could close that fence, the
renderer uses a longer run of tildes than any run present at the start of a body line. No language
identifier is attached to the fence.

On reads, typed Blueprint views expose the original line array without fence delimiters. The full
source view continues to expose the stored Markdown document.

Markdown inside an external body is opaque to the protocol parser. Headings, standard links,
Wiki Links, task markers, block IDs, and frontmatter-like text inside the fence do not participate
in structural validation or Evidence resolution.

## Document Layout

Blueprint and Todo documents use schema version 3:

```yaml
schema: blueprint/v3
```

```yaml
schema: blueprint/todo/v3
```

Protocol-owned Markdown remains outside external body fences. A Results section contains one
fenced body followed by an optional service-generated Evidence list:

```markdown
## Results

~~~
Implementation and verification are complete.
~~~

- Evidence:
  - [Tests passed](todos/todo-2.md#^evidence-3)
```

An Evidence entry contains a protocol-owned H3 and block ID followed by one external body:

```markdown
### Tests passed ^evidence-3

~~~
All cargo tests passed.
~~~
```

The service is the only writer of the H3, block ID, Evidence list, and Todo Evidence index. Caller
content cannot add protocol entries because it remains fenced.

## IDs

Blueprint IDs retain ULIDs because they define the durable aggregate and directory scope:

```text
bp-01KXW318SBY9PGFM0V8M0NPN22
```

All other generated IDs use a type prefix and an unpadded positive decimal number:

```text
todo-1
dod-1
evidence-1
revision-1
```

Each type has an independent sequence within one Blueprint. Evidence IDs and Revision IDs are
aggregate-wide: their respective sequences cover the central Blueprint document and every Todo
document. IDs in different Blueprints may repeat because all operations and references are scoped
by Blueprint ID.

Allocation occurs while holding the Blueprint aggregate lock. The allocator scans existing IDs of
the requested type, selects the largest numeric suffix, and adds one. Existing IDs are never
renumbered. Gaps are valid. The current protocol has no deletion operation, so it does not persist a
separate high-water mark.

Structural parsing rejects duplicate IDs, zero, negative values, non-decimal suffixes, and malformed
prefixes. Offline creation of objects in separate copies of the same Blueprint is outside the
protocol's concurrency guarantees; a later merge that creates duplicate IDs is rejected.

## Evidence Operations

### `evidence_submit`

`evidence_submit` replaces `evidence_add`. It accepts:

```json
{
  "blueprint_id": "bp-01KXW318SBY9PGFM0V8M0NPN22",
  "todo_id": "todo-2",
  "title": "Tests passed",
  "body": {
    "lines": ["All cargo tests passed."]
  },
  "expected_etag": "..."
}
```

`todo_id` is optional. An omitted value submits central Blueprint Evidence. `title` is required,
non-empty protocol text. `body` is a required, non-empty external body.

While holding the aggregate lock, the operation:

1. validates Blueprint state, scope, and ETag;
2. allocates the next aggregate-wide Evidence ID;
3. appends the fenced Evidence entry to the selected document;
4. rebuilds the central Todo Evidence index;
5. validates the complete Evidence aggregate;
6. commits the candidate documents using the store's safe write ordering.

The response contains:

- Evidence ID and title;
- scope (`blueprint` or `todo`) and optional Todo ID;
- owning document path;
- body preview;
- the standard reference from `blueprint.md`;
- the local reference from the owning document.

### `evidence_list`

`evidence_list` accepts a Blueprint ID, an optional Todo ID, and a one-based page number. Without a
Todo ID it scans central and Todo Evidence across the aggregate. With a Todo ID it returns only that
Todo's Evidence.

Entries are sorted by the numeric Evidence suffix and paginated. Each summary contains the same
identity, scope, path, preview, and reference fields returned by `evidence_submit`. The list response
also reports `index_status` as `current` or `stale`; a stale response includes the missing, extra, or
dangling index IDs. Full bodies remain available through the corresponding Blueprint or Todo read
view; v3 does not add an `evidence_get` tool.

### Central Todo Evidence index

Todo Evidence remains stored only in its Todo document. `blueprint.md` contains a service-generated
index rather than duplicated bodies:

```markdown
## Evidence

### Todo Evidence Index

- [Tests passed](todos/todo-2.md#^evidence-3)
```

The index is derived from all Todo documents and rebuilt after Evidence mutations. Aggregate
validation checks that the index exactly represents the current Todo Evidence set. A missing,
stale, duplicated, or dangling index entry is an explicit consistency error rather than something
the parser silently repairs during a read.

For Todo Evidence, the store writes the Todo document first and the derived central index second. If
the second write fails in-process, it restores the previous Todo document and reports failure. A
process crash between the two atomic file replacements can leave valid Todo Evidence with a stale
central index, but cannot leave a dangling central link. Queries report the stale index rather than
mutating files. Before the next locked mutation, the service rebuilds a stale derived index from the
Todo documents and then continues the requested mutation. Because the index contains no semantic
source data, this recovery does not create a Revision entry. The protocol does not claim cross-file
crash atomicity.

## Structured Results References

Blueprint and Todo Results updates accept a body plus Evidence IDs:

```json
{
  "results": {
    "body": {
      "lines": ["Implementation and verification are complete."]
    },
    "evidence_ids": ["evidence-1", "evidence-3"]
  }
}
```

The service resolves every ID against the current Blueprint aggregate, determines its owning
document, and generates the correct standard Markdown link outside the body fence. Callers do not
construct document paths or fragments.

Results reject duplicate IDs and IDs that do not exist in the same Blueprint. Link text comes from
the Evidence title. Central Results use a local `#^evidence-N` link for central Evidence and a
`todos/todo-N.md#^evidence-N` link for Todo Evidence. Todo Results use a local link for Evidence in
the same Todo, `../blueprint.md#^evidence-N` for central Evidence, and a sibling Todo path for other
Todo Evidence.

The on-disk parser validates the generated links as defense against manual corruption. Only links
outside external body fences count as protocol Evidence references.

## Completion and Closure

Todo completion continues to require:

- current `in_progress` state;
- complete child work and Completion Criteria;
- non-empty Results body;
- at least one Results Evidence reference;
- a non-empty completer.

A complete Blueprint close continues to require:

- no open Todo;
- no open Definition of Done item;
- a non-empty Blueprint Results body;
- at least one Blueprint Results Evidence reference to existing aggregate Evidence.

Validation reports distinct failures for a missing Results body, missing Evidence references,
unknown Evidence IDs, invalid document targets, malformed stored links, and inconsistent indexes.
The missing-reference error is actionable and includes one valid stored form:

```text
complete Blueprint close requires at least one Results Evidence reference.
Submit Evidence with evidence_submit, then add its ID to results.evidence_ids.
Stored Markdown example: [Acceptance evidence](#^evidence-1)
```

An incomplete close still requires a reason. Documentation and errors must not suggest reopening a
Definition of Done item as a workaround for malformed or missing Evidence references.

## Public API Changes

Version 3 intentionally removes compatibility behavior:

- v2 document schemas are rejected;
- external body fields use line-array objects instead of strings;
- Results use a body plus `evidence_ids`;
- `evidence_add` is removed;
- `evidence_submit` and `evidence_list` are exposed;
- new Todo, DoD, Evidence, and Revision IDs are sequential;
- no migration command or legacy alias is provided.

Tool descriptions and generated documentation must show the body line-array shape, Evidence submit
and list workflow, structured Results references, and the complete-close Markdown example.

## Error Handling

Errors identify the operation, field, document, and object ID when applicable. Required behaviors
include:

- reject an empty external body where the field is required;
- reject line breaks in protocol text;
- reject an unknown or cross-Blueprint Evidence ID before writing;
- reject duplicate sequential IDs found during parsing or allocation;
- reject malformed or noncanonical service-owned Evidence links;
- reject a missing or stale central Todo Evidence index;
- distinguish ETag conflicts from structural validation errors;
- preserve the previous valid file when candidate validation fails;
- report a stale derived index on queries and rebuild it before the next locked mutation;
- never report a two-document Evidence submission as successful unless both writes complete.

External body content is preserved exactly after joining the input lines. The service does not
decode literal backslash escape sequences because they may be intentional code, prose, or regular
expression content.

## Verification

Focused tests must cover:

1. H1/H2 headings, links, Wiki Links, task markers, and block IDs inside an external body do not
   alter protocol parsing.
2. A body containing `~~~` selects a longer delimiter and round-trips exactly.
3. Body line arrays produce actual LF characters without unintended literal `\n` separators.
4. Protocol text rejects embedded line breaks.
5. Todo, DoD, Evidence, and Revision sequences allocate independently and monotonically while the
   Blueprint retains a ULID.
6. Duplicate or malformed sequential IDs are rejected.
7. `evidence_submit` writes central and Todo Evidence with a required title and fenced body.
8. `evidence_list` aggregates, filters, sorts numerically, paginates, and returns canonical
   references.
9. Todo Evidence appears exactly once in the central derived index without duplicating its body.
10. Results IDs render correct links for central, local Todo, and sibling Todo Evidence.
11. Fenced links do not satisfy completion or close gates.
12. Todo completion and complete Blueprint close pass with valid structured references.
13. Each close failure has a distinct error, and the missing-reference error contains
    `[Acceptance evidence](#^evidence-1)`.
14. An in-process central-index write failure restores the previous Todo document, while a simulated
    crash gap is reported by queries and repaired before the next locked mutation.
15. v2 documents and `evidence_add` are unavailable.
16. Generated MCP documentation and tool schema checks reflect all v3 request and response shapes.

The final verification sequence includes formatting, focused Blueprint tests, generated-document
checks, the complete Rust test suite, and Clippy with warnings denied.

## Out of Scope

- migration or compatibility for Blueprint v2;
- lightweight Todo completion without Evidence;
- a shortened Blueprint ID;
- distributed or offline merge-safe object allocation;
- Evidence semantic scoring by the MCP service;
- an `evidence_get` tool;
- generic user-authored Markdown sections outside fenced external bodies.

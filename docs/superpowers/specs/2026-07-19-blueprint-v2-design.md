# Blueprint v2 Design

## Goal

Upgrade Blueprint from a single Markdown file with fully embedded Todos into a
project-local, multi-document planning protocol that remains readable and
editable in Obsidian.

Blueprint v2 must preserve the useful parts of v0.1:

- explicit Intent, Constraints, Definition of Done, and high-level Plan;
- one central Todo Graph with Obsidian task markers as the authoritative Todo
  execution state;
- dependency-derived readiness and resumable multi-agent handoff;
- Markdown as the protocol source of truth;
- ETag-protected, lock-serialized writes.

It adds three missing parts:

- a task-specific Rubric generated by the routing Agent or Skill;
- explicit Evidence that Results can cite;
- append-only Revision History explaining semantic changes without relying on
  Git commits.

Large Todo content moves to one document per Todo while identity, status, and
graph relationships remain centralized in `blueprint.md`.

## Non-goals

- Blueprint is not a general workflow engine and does not execute Skills or
  scripts itself.
- Rubric is not restricted to numeric scoring or pass/fail evaluation.
- Evidence is not automatically interpreted as proof, truth, or support.
- Revision History is not a text diff, event-sourcing system, or replacement
  for filesystem history.
- v1 workspace compatibility and automatic migration are not required because
  v1 has not been deployed.
- Todo files do not independently own status, Owner, dependencies, or parent
  relationships.

## Workspace Layout

The workspace uses schema `blueprint/v2`:

```text
<vault>/
└── .blueprint/
    ├── manifest.md
    ├── blueprints/
    │   └── bp-<id>/
    │       ├── blueprint.md
    │       └── todos/
    │           ├── todo-<id>.md
    │           └── todo-<id>.md
    ├── .locks/
    │   └── bp-<id>.lock
    └── .tmp/
```

`manifest.md` remains the workspace protocol marker:

```markdown
---
schema: blueprint/v2
---

# Blueprint Workspace
```

Blueprint and Todo paths never change when lifecycle state changes. Stable
paths keep standard Markdown links, dependency references, and cross-document
Evidence references valid.

## Blueprint Frontmatter and Lifecycle

`blueprint.md` has minimal frontmatter:

```yaml
---
schema: blueprint/v2
id: bp-01K...
state: active
---
```

Supported lifecycle states remain:

- `active`: work may continue;
- `closed`: the Blueprint has formally ended, with a complete or incomplete
  Closure recorded in Results;
- `cancelled`: the overall Intent was explicitly abandoned.

The frontmatter state is lifecycle metadata. It is not Execution State.
Execution State is always derived from Definition of Done and the central Todo
Graph.

`blueprint_close` and `blueprint_cancel` update frontmatter and append their
existing Results records. They do not move directories. Mutations other than
reads are rejected for non-active Blueprints. `blueprint_list` filters by the
frontmatter state.

## First-class Document Sections

The source layer must parse a Markdown document into an ordered section model
rather than matching a single hard-coded Blueprint template:

```text
ParsedDocument
├── Frontmatter
├── H1
└── Section[]
    ├── title
    ├── heading source range
    ├── body source range
    └── original source
```

Document schemas declare which H2 Sections are required and unique. Unknown
Sections remain legal and must be preserved byte-for-byte when unrelated
content is edited. Typed domain parsers consume Sections without owning the
general Markdown slicing logic.

Blueprint and Todo edits continue to be targeted source edits. The
implementation must not parse and re-render an entire document.

## Blueprint Document

`blueprint.md` contains these required Sections in this canonical creation
order:

```text
Record
Intent
Constraints
Definition of Done
Plan
Rubric
Todos
Results
Evidence
Revision History
Notes
```

Their responsibilities are:

```text
Record               Blueprint responsibility metadata
Intent               the user's desired outcome and scope
Constraints          boundaries that execution must not violate
Definition of Done   explicit aggregate completion conditions
Plan                 high-level method and route
Rubric                task-specific evaluation program selected by an Agent
Todos                 the authoritative Todo Graph
Results               aggregate outcomes, decisions, and open questions
Evidence              Blueprint-level evidence cited by aggregate Results
Revision History      reasons for semantic changes to the Blueprint
Notes                 unstructured information not yet promoted elsewhere
```

Record continues to store `Created By`, `Closed By`, and `Cancelled By`.
Frontmatter stores machine lifecycle metadata; Record stores human-readable
responsibility metadata.

## Central Todo Graph

The `Todos` Section remains the only source of truth for Todo identity, state,
and graph relationships. Each executable Todo is an Obsidian task with a
standard Markdown link to its detail document:

```markdown
- [/] [Complete the draft](todos/todo-01K1DRAFT.md) ^todo-01K1DRAFT
  - Created By: planner
  - Owner: writer
  - Depends On: todo-01K1RESEARCH
```

The central graph owns:

- Todo ID and title;
- the link to the Todo document;
- the task marker (`pending`, `in_progress`, `completed`, `blocked`, or
  `cancelled`);
- Created By, Owner, and Completed By;
- Depends On;
- parent/child nesting under Children;
- Block Reason and Cancel Reason.

The central graph does not embed potentially large Completion Criteria,
Handoff, Results, Evidence, Revision History, or Notes.

Child Todos remain nested under `Children:` and each child links to its own
Todo document. Dependency and child graph validation retains the v0.1 rules.

## Todo Document

Each Todo has a stable file named after its ID. Minimal frontmatter identifies
the document without duplicating graph state:

```yaml
---
schema: blueprint/todo/v2
id: todo-01K...
blueprint: bp-01K...
---
```

Todo files contain these required Sections:

```text
Intent
Completion Criteria
Plan
Handoff
Results
Evidence
Revision History
Notes
```

The Todo H1 must match the Markdown link label in the central graph. Title
updates modify both locations under the Blueprint lock.

Todo document responsibilities are:

```text
Intent               the local outcome of this Todo
Completion Criteria  local task checkboxes required before completion
Plan                 the local execution approach
Handoff              minimum continuation context for another Agent
Results               local outcomes and conclusions
Evidence              evidence produced or collected by this Todo
Revision History      reasons for semantic changes to this Todo
Notes                 unstructured local context
```

Todo frontmatter never stores status, Owner, dependencies, parent, Block
Reason, or Cancel Reason. Duplicating those fields would create conflicting
sources of truth.

## Rubric

Rubric is a task-specific evaluation program authored by the routing Agent or
Skill after inspecting the user's goal. The router may choose existing Skills,
specialized Agents, scripts, and tools, then materialize the chosen evaluation
flow in this Section.

Rubric is deliberately Markdown-first. It may describe:

- evaluation intent and review lenses;
- selected evaluator Skill, Agent, script, or tool identifiers;
- why each evaluator applies to this goal;
- required observations or Evidence;
- expected outputs;
- limitations and prohibited interpretations;
- how disagreement and uncertainty should be preserved.

Rubric is not required to use scores or binary correctness. A literary Rubric
may ask for continuity review and reader simulation; a code Rubric may ask for
tests and static analysis.

Blueprint MCP stores and exposes Rubric but does not execute it. The operating
Agent reads it, loads the referenced capabilities, performs the evaluation,
and writes Results and Evidence.

Rubric is required and must be non-empty. For a task that needs no specialized
evaluator, it must still state how Definition of Done and Constraints will be
reviewed.

## Evidence

Evidence is stored inline in the independent `Evidence` Section of the
Blueprint or Todo document that collected it. It is not stored in a central
Evidence file.

Each Evidence item has a globally unique `^evidence-*` Block ID within the
Blueprint directory. Its Markdown body remains flexible so the same protocol
can represent command output, textual observations, user feedback, artifacts,
or ambiguous literary interpretations.

Example:

```markdown
## Evidence

### The protagonist repeatedly expresses family attachment ^evidence-01K1A

- Collected By: literary-continuity
- Observation: Two first-chapter scenes emphasize fear of losing family ties.
- References:
  - [Family argument](../../story.md#Family-argument)
  - [Late-night conversation](../../story.md#Late-night-conversation)
- Limitations:
  - The same passages may indicate suppressed desire to leave.
```

Results cite Evidence using standard Markdown relative links with heading or
Block ID fragments:

```markdown
- Evidence:
  - [Family attachment](#^evidence-01K1A)
  - [Background research](todo-01K1RESEARCH.md#^evidence-01K1B)
```

Evidence may cite Evidence in another Todo. Evidence references do not affect
Todo readiness and do not imply support, contradiction, or truth. Those
relationships remain explicit in prose unless a future protocol proves that a
typed relation is necessary.

Protocol-generated links must use standard Markdown link syntax; Blueprint v2
does not generate or require Wiki Links. The parser validates Evidence ID
uniqueness and that internal Evidence links resolve within the Blueprint
aggregate. External project References are not required to resolve through the
Blueprint store.

A completed Todo must have non-empty Results and at least one valid Evidence
item or Evidence reference. This is structural evidence presence, not a claim
that the Evidence is semantically sufficient. Rubric and Agent review determine
sufficiency.

## Revision History

Revision History is an independent, append-only Section in both Blueprint and
Todo documents. It replaces the v0.1 assumption that Git commits reliably
capture protocol history.

Revision History records reasons for semantic changes, not every write. It
applies to changes such as:

- Blueprint Intent, Constraints, Definition of Done, Plan, or Rubric;
- Todo Intent, dependencies, Completion Criteria, or Plan;
- material reinterpretation or invalidation of Results and Evidence;
- creation, cancellation, or restructuring of planned work when the reason is
  not already obvious from the operation record.

Execution transitions, Handoff refreshes, Evidence collection, Result updates,
and ordinary wording fixes are not automatically revisions.

Each entry receives a `^revision-*` Block ID and records at minimum:

- Changed By;
- Reason;
- Change summary;
- affected Section or Todo IDs;
- Evidence impact when existing Evidence or Results may no longer apply.

Typed mutations that change semantic fields require `changed_by` and
`change_reason` and append the Revision entry atomically with the edit. Public
tools cannot replace or delete existing Revision entries. Unknown Markdown in
Revision History remains preserved.

## Results and Completion

Todo Results store local outcomes and cite relevant Evidence. Blueprint Results
store aggregate outcomes, deliverables, decisions, and open questions and may
cite Evidence from any Todo document.

`todo_complete` requires:

- current graph state is `in_progress`;
- all Completion Criteria in the Todo file are checked;
- all non-cancelled child Todos are completed;
- Todo Results are non-empty;
- at least one Evidence item or valid Evidence reference exists;
- `completed_by` is non-empty.

`blueprint_close` retains complete and incomplete Closure semantics. A complete
Closure requires all Definition of Done items checked and all Todos completed
or cancelled, non-empty Blueprint Results, and at least one valid Evidence
reference from Blueprint Results. Incomplete closure requires a reason and may
record missing Results or Evidence among the open work. Closing does not claim
that MCP semantically agrees with the Rubric; it records the Agent's explicit
closure after the structurally required Results and Evidence are present.

## Execution State and Views

Execution State remains derived and is never persisted. The service reads the
central graph for Todo status and dependencies, and loads Todo detail files
only for fields required by the requested operation or view.

`blueprint_status` returns lifecycle state plus derived DoD counts, Todo counts,
ready/not-ready dependencies, blocked, unassigned, and open Todo IDs.

`blueprint_get(view: "full")` returns `blueprint.md`, its ETag, and a Todo
document index. It does not concatenate every Todo source into one large
response.

`blueprint_get(view: "resume")` returns Blueprint Intent, Constraints, open
Definition of Done, Plan, Rubric, current Results, and compact active/ready/
blocked Todo summaries. Handoff is loaded from the relevant Todo files.

`todo_get` returns central graph metadata together with the Todo document,
document ETag, Results, Evidence, and derived readiness.

## Storage, Locking, and ETags

All mutations within one Blueprint use one Blueprint lock. This keeps graph
updates, detail edits, cross-document Evidence validation, and lifecycle
changes serialized without introducing a multi-lock protocol.

`blueprint.md` and each Todo file have independent content ETags:

- graph and Blueprint Section mutations accept `expected_blueprint_etag`;
- Todo document mutations accept `expected_todo_etag`;
- operations touching both accept both ETags when supplied and validate them
  after acquiring the Blueprint lock.

Todo creation stages the Todo document first and commits the central graph link
last. In-process failures remove the staged file. Reads and writes reject a
graph entry whose Todo file is missing and reject an unreferenced `todo-*.md`
file as an orphan, returning a repairable consistency error rather than
silently ignoring it.

Todo completion writes validated Todo Results/Evidence first and changes the
central task marker last. A process interruption can therefore leave completed
content on an in-progress Todo, which is safe to retry; it must never leave a
completed graph marker without valid Todo content.

Each individual file replacement remains atomic through `.tmp`. The protocol
does not claim crash-atomic multi-file transactions.

## MCP Contract Changes

The v2 service retains the existing Blueprint, DoD, and Todo operation names
where their purpose still applies. Their inputs and outputs change to address
the aggregate layout and document ETags.

Key changes:

- `blueprint_create` requires non-empty Rubric and creates a Blueprint
  directory plus `blueprint.md`;
- `blueprint_get` returns a Todo document index instead of one fully embedded
  graph model;
- `blueprint_list` filters frontmatter state rather than lifecycle directory;
- `blueprint_update` can update Rubric and requires revision metadata for
  semantic changes;
- `blueprint_close` and `blueprint_cancel` update frontmatter without moving
  paths;
- `todo_create` creates both a graph node and Todo document;
- `todo_get` joins graph metadata with Todo document data;
- `todo_update` separates graph fields from Todo document fields and requires
  appropriate ETags;
- `todo_complete` validates the Todo document's Completion Criteria, Results,
  and Evidence;
- `dod_update` remains an execution update and does not automatically create a
  Revision entry.

Add focused operations for append-oriented content:

```text
evidence_add
revision_append
```

Both accept a document scope (`blueprint_id` and optional `todo_id`).
`evidence_add` generates a globally unique Evidence Block ID and appends one
item to the scoped Evidence Section. `revision_append` generates a Revision ID
and appends one entry, but typed semantic mutations should normally append
their required Revision automatically.

No generic public `section_replace` tool is added. First-class Sections are an
internal source-model capability; typed domain operations continue to protect
protocol invariants.

## Validation and Errors

Every read and candidate write validates:

- workspace, Blueprint, and Todo schema versions;
- Blueprint and Todo IDs against paths and frontmatter;
- required and uniquely occurring Sections for each document type;
- central graph task syntax and Todo document links;
- exactly one graph entry and exactly one Todo file per Todo ID;
- graph dependency, parent/child, readiness, and status invariants;
- Completion Criteria placement and checkbox syntax;
- global Evidence and Revision ID uniqueness;
- internal Evidence link resolution;
- completed Todo Results and Evidence requirements;
- active Blueprint preconditions for mutations;
- ETags under the Blueprint lock.

Errors identify the document path, Section, and ID when applicable. Candidate
writes are rejected before target files are replaced. Multi-file operations
report recoverable graph/detail inconsistency explicitly.

## Compatibility

The workspace manifest is bumped to `blueprint/v2`. Encountering a v1 manifest
returns an explicit unsupported-schema error. The service does not mutate,
delete, or automatically migrate v1 content.

## Test Strategy

Implementation follows test-driven development. Tests cover:

1. first-class Section parsing, required schemas, unknown content preservation,
   and targeted edits;
2. v2 workspace creation and stable aggregate paths across lifecycle changes;
3. central graph and Todo document creation, joining, title updates, and orphan/
   missing-file errors;
4. graph state transitions and readiness with criteria stored in Todo files;
5. Rubric creation, update, resume exposure, and required Revision entries;
6. Evidence creation, global uniqueness, cross-Todo links, unresolved internal
   links, and completion gating;
7. append-only Blueprint and Todo Revision History;
8. independent Blueprint/Todo ETags and Blueprint-wide serialization;
9. safe write ordering for create and complete operations;
10. frontmatter lifecycle filtering, closing, and cancellation without path
    movement;
11. MCP tool schemas and forwarding for the changed and new operations;
12. the full repository test, lint, formatting, and documentation-generation
    suite.

## Success Criteria

The design is complete when:

- a Blueprint has a stable directory and frontmatter lifecycle state;
- `blueprint.md` is the authoritative Todo Graph while every Todo has an
  independent detail document;
- Todo task markers remain the authoritative execution state;
- Rubric guides Agent-selected evaluation without imposing universal scoring;
- Todo and aggregate Results can cite independently stored Evidence Sections;
- semantic changes produce append-only Revision History without relying on Git;
- derived status, resume, locking, ETags, and source-preserving Markdown edits
  continue to work across the multi-document aggregate;
- all focused and repository-wide verification passes.
